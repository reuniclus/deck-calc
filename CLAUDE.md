# CLAUDE.md

Working agreements for this repo. Read this and `CODEMAP.md` before touching code; `PLAN.md` holds the architecture and algorithms.

## Commands

| task | command |
|---|---|
| dev server | `npm run dev` |
| production build | `npm run build` |
| preview the build | `npm run preview` |
| tests (once) | `npm test` |
| tests (watch) | `npm run test:watch` |
| typecheck | `npm run typecheck` |
| build the single-file math harness | `npm run harness` → `dist-harness/harness.html` |
| build + verify the harness in jsdom | `npm run harness:smoke` |

`npm run build` runs `tsc -b` first, so a type error fails the build.

## Hard rules

1. **`src/math/**` is pure.** No React, no DOM, no imports from outside `src/math`. It has to stay portable into a Web Worker and directly testable.
2. **`src/math/exact.ts` is test-only.** BigInt oracle. Never import it from app code.
3. **Groups are disjoint.** The multivariate hypergeometric requires a partition of the deck. Violating this produces wrong numbers with no error. Enforce in the model, assert in the DP.
4. **`others` is derived, never stored.** `others = deckSize - Σ group counts`.
5. **Never clamp numeric inputs while the user is typing.** Hold input as a string in local state, commit on valid parse. Invalid deck states are allowed and shown, not silently corrected.
6. **Queries reference groups by stable `id`, never by name or array index.** The AST is the source of truth; display text is regenerated via `printExpr` with current names. Renaming a group must not change any result; deleting a referenced group must surface an explicit error, never silently different numbers.
7. **`vite.config.ts` `base` must match the repo name** (`/deck-calc/`) or the Pages build serves a blank page.
8. **The harness is generated, never hand-edited.** `src/harness/` is the source; the single-file HTML is a build artifact. It imports the real `src/math` modules so it cannot drift from tested code.
9. **The real UI (`src/ui/`, `src/state/`) needs a real render test, not just `tsc`.** Typecheck passing does not mean the wiring works — this session alone, a real React Testing Library render caught two bugs (an unparseable seed query; a rename that silently broke the query instead of re-deriving it) that `tsc -b` and `vite build` both missed. Every new interactive piece gets at least one test that actually renders it and fires the events a user would.
10. **jsdom does NOT load Vite's CSS imports, run real layout, or implement `IntersectionObserver`.** `getComputedStyle` in tests reflects only inline styles and jsdom's minimal UA defaults — it will NOT tell you whether a stylesheet rule applies, let alone whether something visually overflows. `IntersectionObserver` is `undefined` entirely (confirmed directly) — `src/test-setup.ts` stubs it just to stop components from crashing on mount; the stub never fires a callback, so anything gated on a real intersection change (e.g. `MobileNav`'s "scrolled past the rail" detection) cannot be genuinely exercised in tests. Tests for CSS- or viewport-driven behavior can only confirm the right elements/classes exist for the behavior to attach to (structural), never that the behavior itself fires correctly (pixel/geometry-level). Wasted a round writing tests that asserted computed style from `index.css` rules before catching this — don't repeat it.
11. **`window.location` (including `.hash`) persists across test cases within the same jsdom run.** Any feature that reads or writes it (e.g. `AppState`'s URL-hash sharing) needs an explicit reset between tests, or one test's leftover hash silently changes the NEXT test's starting state. Confirmed directly: wiring in hash-sync without a reset broke 27 unrelated tests in one run, because each `render(<App/>)` picked up whatever hash the previous test had left behind. `src/test-setup.ts` resets it in a global `beforeEach` — don't remove that thinking it's dead code.
12. **UI scale is 1.5x via `zoom` on `html` (src/index.css), not a rewrite of the ~73 hardcoded px values to rem.** Chosen deliberately over `transform: scale()`: `zoom` recalculates actual layout at the scaled size (containers/scrollbars adjust correctly) and keeps `getBoundingClientRect()`/`clientX` reported in the SAME scaled coordinate space as the rest of the page — so `App.tsx`'s pointer-drag rail-resize math and `ResultView.tsx`'s chart-hover math needed zero changes. Verified with real Playwright screenshots (a Chromium install exists at `/opt/pw-browsers/`, `playwright` installs via `npm install --no-save playwright` -- npmjs.org domains are allow-listed): at the identical 900px viewport, unscaled shows the desktop two-column layout while zoomed shows the mobile single-column layout, confirming the mobile breakpoint and rail bounds correctly operate in the same effective-CSS-pixel space that zoom scales.
13. **jsdom has no `Worker` at all (confirmed directly, same class of gap as `IntersectionObserver`).** Every test involving `mulliganWorkerClient.ts` exercises ONLY the synchronous fallback path (`SyncFallbackMulliganWorker`) -- the real `Worker` code (`mulliganWorker.ts`, the actual point of that whole module) has zero test coverage in this suite and cannot get any without a real browser. Verified separately, twice now, with a real headless Chromium + Playwright (not committed as a test, since it needs a real browser this project doesn't have in CI): (1) confirmed the worker script is genuinely requested over the network and `requestAnimationFrame` kept firing with zero stalls during a real 2-mulligan single computation; (2) after that fix still left `GridTab`'s per-row computation synchronous (it stays MOUNTED in the background regardless of which tab is visible, per PLAN.md's "kept mounted" design -- confirmed directly with `console.time` instrumentation that this alone caused a real, measurable stall even while looking at the Chart tab), re-verified after batching that computation through the worker too: max frame gap dropped from ~180-200ms to ~91ms, with the 100ms+ "visible jank" category empty entirely. If this class of feature needs touching again, re-verify the same way rather than trusting jsdom's green checkmarks alone -- and remember that "moved ONE computation to a worker" does not mean every synchronous computation touching the same state got moved too; check every component that stays mounted and reacts to the same inputs.
14. **A `str_replace` on `index.css` once matched only `.no-wrap-group`'s line but was given a `new_str` that fully replaced it with an unrelated new rule instead of adding alongside it -- silently deleted a still-in-use CSS class (AdvisorStrip's own layout).** All 273 tests still passed, because jsdom does not render real CSS/layout at all (see the mobile-testing limitations above) -- a deleted rule that doesn't change any DOM text or structure is functionally invisible to this test suite. Caught only by directly grepping the file afterward to confirm both rules existed, not by the tests going green. When editing shared CSS files via str_replace, re-view (or at minimum re-grep) the surrounding rules immediately after the edit rather than trusting a passing test run -- this class of mistake is exactly the kind jsdom cannot catch, ever, regardless of how much test coverage exists elsewhere.
15. **Indexing a `Float64Array` (any "curve") with a non-integer silently returns `undefined`, not an error.** Found in `cantrips.ts`: `cardsSeenByT + k*bonus` is always integer when `bonus` comes directly from a single user input, but becomes fractional the moment several effect types get pooled into one average-bonus summary stat (e.g. `(6*3+1*4)/7 = 3.142857...`). The existing `?? 0` fallback -- there for a different, legitimate reason (an out-of-range index) -- silently converted that `undefined` into a WRONG near-zero result instead of a visible error, and the bug was severe enough to flip a monotone relationship backwards ("more cards examined" scored lower than "fewer"). Every existing test used integer bonus values exclusively and could not have caught this; it was found only by real-browser verification, where the resulting number looked implausible on inspection. Whenever a curve gets indexed by a value derived from an average, ratio, or other non-count-like arithmetic -- not just a raw draw count -- check whether that value can be non-integer before shipping, and round explicitly at the index site rather than trusting the value's origin to always be a whole number.
16. **`event.clientX`/`clientY` used directly as a `position: fixed` CSS length gets zoomed TWICE under `html { zoom: 1.5 }`, and this exact bug was found and fixed ONCE already (rail-dragging, `computeRailWidthFromDrag`) before recurring in a different place (the chart tooltip) that nobody thought to re-check.** `clientX` is already reported in final, post-zoom viewport pixels; setting a CSS `left`/`top` to that raw value gets zoomed again when the browser renders it, producing an offset that grows with distance from the origin (measured directly: 356.5px off at x=684.5, confirmed to shrink to ~14.5px, matching an unrelated intentional CSS offset, once corrected). The lesson isn't "remember to divide by zoom" -- that was already known and documented after the first occurrence. It's that fixing one instance of a bug class doesn't fix the class: **grep for every other place `clientX`/`clientY` get assigned directly to a CSS length** (`left`, `top`, `width`, `transform: translate`, etc.) whenever this pattern is touched again, rather than assuming the one documented fix covers the whole app. A shared `zoom.ts` utility now exists specifically so future call sites have an obvious, already-tested thing to reach for instead of re-deriving (or missing) the correction again.
17. **A closed form that reproduces the endpoints of a distribution can still be wrong everywhere in between, and "validated with real numbers" does not mean validated.** cantrips.ts's flat `curve[n + k*bonus]` was checked against hand-computed cases when built and looked right; measured against a real play-out of every deck ordering (`bruteSelection.ts`) it is off by up to 8 percentage points, with a sign that FLIPS by effect type and threshold. The per-k breakdown showed why: at k=0 and k=2 copies drawn it agrees exactly, at k=1 it agrees with nothing -- because conditioning on "k copies among the first n cards" silently mixes two different pools (scheduled slots draw from the non-effect pool; window slots draw from a remainder that still contains the other copies), and the two pools coincide at exactly the endpoints anyone would spot-check. Neither candidate form survived. The lesson is procedural: for any model where cards are examined in an ORDER (selection effects, mulligans, anything with "then draw"), the arbiter is a brute-force play-out containing NO hypergeometric of its own, checked first against `evaluate()` with the mechanic disabled (agreement to 5e-16 there is what makes it an arbiter rather than a second opinion). Do not trust a closed form here because it matches intuition, matches the endpoints, or produces a plausible-looking curve.
18. **Ask whether the DP needs the dimensions it seems to need.** The exact selection model looked like it required tracking group counts through a sequential process (a state space in the tens of millions); it needs NONE, because the query's composition is conditionally hypergeometric given the slot structure alone, so the two concerns factor completely -- slots from a tiny DP, composition from one ordinary `evaluate()`. The resulting DP is also query-independent, which is what makes caching it across grid rows possible. When a state space looks too big, check whether part of it is conditionally independent of the rest before reaching for approximation or Monte Carlo.
19. **When state gets packed into a single key, size every field for the range AFTER canonicalization, not before.** `exactSelectionCurveAnd` folds a satisfied group's leftover copies into the filler pool (exact, and its biggest speedup), which pushes the filler count above the deck's original filler total -- while the packed mixed-radix key had that field sized for the unfolded maximum. Distinct states therefore collided and silently returned each other's memoized values, wrong by ~1.5 percentage points, with results that stayed plausible AND monotone. Nothing but the brute force caught it. Two habits follow: derive packed-key field widths from the reachable maximum (including anything canonicalization can add) rather than from the input parameter that looks like the bound, and never introduce a state-space optimization without re-running the independent check immediately afterward -- a canonicalization is exactly the kind of change that alters which states exist.
20. **A model that OPTIMIZES cannot be verified against a fixed policy by equality.** Once the selection model made real keep decisions (which card to take when an effect can only take one), matching the brute force's greedy keep-in-window-order policy exactly would have been evidence of a BUG, not of correctness. Verify an optimizer by sandwiching it: a fixed reasonable policy below, a clairvoyant variant that decides with the future visible above. Equality checks still apply, but only for configurations where no choice exists (whole-window-kept effects) -- decide which regime a case is in before writing the assertion, or a passing suite will mean nothing.
21. **A bound that says "at most" changes a model's structure, not just its predicate.** Adding `hi` support to the selection DP invalidated three separate things that had been quietly load-bearing: success stopped absorbing (you can be satisfied on turn 3 and busted on turn 4), satisfied groups stopped being foldable into the filler pool (the main speedup), and keeping a useful card stopped being automatically optimal, making DECLINE a real move. It also inverts results: for a query with a brick group, drawing cards is WORSE than having no effect at all (0.163 vs 0.292), because scheduled draws are forced while looking can refuse -- the opposite of the unbounded case where draw dominates scry. And bounded curves DECREASE in draws, so anything phrased as "draws needed to reach X%" is invalid for them. Before adding an upper bound to any model here, check every early-exit, every canonicalization, and every monotonicity assumption downstream.
22. **Which verification a case admits depends on the query regime, not only on the code under test.** Ponder-no-shuffle is exactly checkable against a fixed greedy policy for monotone queries (window order is irrelevant when every card is welcome) and only SANDWICHABLE once a brick makes ordering a decision. Same function, same effect, different regime, different valid assertion. Classify the regime before writing the expectation, or the assertion will either fail spuriously or pass vacuously.
9. Every new math function gets a test against either the BigInt oracle or brute-force enumeration before it gets a UI.

## Style

- `strict` TS, plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. Assume they're on and write accordingly.
- Comments explain *why*, not *what*. Non-obvious math gets a citation to the relevant `PLAN.md` section.
- No default exports except React route/page components.
