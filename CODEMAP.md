| `src/ui/DeckEditor.tsx` | deck size / hand / mulligans (one line), group rows (name+input grouped, delete isolated — a real spacing bug caught in mockup review), rename re-derives query text, delete auto-prunes references with a visible notice (deliberate reversal of the earlier "never silently prune" rule — see below). Deck size is a native combobox (`<input list>`/`<datalist>`, presets 40/60/99) rather than a plain input plus 3 separate preset buttons -- that layout could show the SAME number twice at once (typed value happened to match a preset, e.g. "99" shown both as the typed value AND highlighted separately) and cost real width for little benefit on mobile. One field can't have that problem -- there's only ever one number on screen. Uses `type="text"` + `inputMode="numeric"`, NOT `type="number"` -- the latter has confirmed real cross-browser datalist inconsistency (Safari in particular often shows only the current value, not the full option list), reported as a real "only has 40" bug before being fixed. Every group row also shows a live "-> N% in opening hand" (`handOdds`/`solveCountForTarget`, both trivial single-atom evaluate()/minSlotsForTarget calls, no new math module) -- no mode toggle, both count and % always visible and both editable; editing % solves for count capped at whatever space the OTHER groups' current counts leave, silently capping to the best achievable (Others hitting 0 IS the "no more room" signal, no red text) rather than ever asking for more than fits. Each row solves INDEPENDENTLY against the others' current snapshot, deliberately not a joint solver -- see PLAN.md's rail redesign section for why. `handOdds` clamps count to deckSize defensively -- a group's count can transiently exceed a shrinking deck size mid-edit (e.g. backspacing deck size to empty), which crashed boxCurve before the clamp was added; caught by the EXISTING backspace-to-empty test, not a new one written for this feature specifically |

When mulligans>0, also shows optimal-mulligan-strategy summary (mulligan.ts) with a plain-English threshold description for the common single-group case (`describeAsThreshold`, returns null rather than force a misleading simplification for multi-group/non-monotone strategies) |
| `src/ui/SuggestionsTab.tsx` | full breakdown: every minimal vector (frontier.ts), best split of current slots, fewest slots for target (allocate.ts) — same scope restriction as the strip (single monotone AND-clause). | `src/ui/MulliganHandTable.tsx` | the per-hand keep/mulligan breakdown table extracted into its own reusable component -- shared between SuggestionsTab and QuestionsTab's "is my hand safe" card, backed by the SAME `useMulliganStrategyCtx()` computation (not computed twice). Deliberately just the table itself, not the surrounding explanatory text, which differs enough between the two callers not to share. Truncates right after the LAST mulligan verdict in sorted order rather than listing every hand -- confirmed from a real screenshot that the tail (once verdicts settle into all-keep) adds nothing. NOT a simple "past total N everything's fine" threshold -- two hands with the same total can disagree (one group's copies can be worth more than another's), so the cutoff is found from the actual computed data, not assumed from a pattern |
| `src/ui/QuestionsTab.tsx` | frequently-asked deck-building questions, each a preset over a general engine rather than a bespoke tool per question (see PLAN.md's "Backlog: frequently asked deck-builder questions" for the full design history across many rounds of mockup review). "Is my hand safe to keep" is fully built (zero new math -- reuses MulliganHandTable). Cantrips is fully built (CantripsCard.tsx / cantrips.ts). "Enough setup for my payoffs" (a resource-vs-consumer joint distribution) remains an explicit "not built yet" placeholder -- its own separately-scoped math project, not yet implemented |
| `src/math/cantrips.ts` | "how many cantrips should I run" -- card-selection effects (draw X, scry/look-and-keep X) in a fixed-size deck, with dilution (every copy has to come from somewhere) and the fact that a cantrip only helps once drawn. Deliberately informs rather than prescribes (a single "optimal" mix always favors the biggest look-size, which isn't always feasible for reasons the tool can't see) -- per-effect-type marginal value (telescopes to (P(4)-P(0))/4 exactly) plus an exact joint multi-effect mix builder. `bestDilutionChoice` picks which group absorbs dilution EXACTLY (tries every candidate directly, keeps whichever gives the highest resulting rate) rather than a user picker or a "most populous" heuristic -- the latter is usually right but not always (confirmed with a real constructed OR-query counterexample where it would have picked measurably worse). `marginalValuePerCopyAutoDilute`/`copiesNeededForTargetAutoDilute` re-run this choice at every count tried, since the best group to dilute can shift as more copies get added. A REAL bug caught only by real-browser verification, not by jsdom tests: `cardsSeenByT + k*bonus` can be a non-integer once multiple effect types get pooled into one average-bonus summary stat, and indexing a Float64Array with a non-integer silently returns `undefined` -- a careless `?? 0` fallback turned that into a wrong near-zero result instead of a visible error. Fixed with `Math.round()` at every curve-index site; now covered by dedicated regression tests using the exact non-integer bonus value that exposed it |
| `src/ui/CantripsCard.tsx` | the cantrips UI: per-effect-type marginal-value table with a live "copies needed for target%" column (no button -- always live, since the search is cheap), a deck-composition breakdown, and a collapsed "build and test an exact mix" section for the full joint computation. No dilution picker -- an earlier version had one, but it was never part of the agreed design (added unilaterally while resolving an open question, not flagged as a deviation) and got removed once called out; the best group to dilute is now computed automatically and shown as read-only text |
| `src/ui/GridTab.tsx` | 2D grid: sweep one group's copies × cards drawn. Sliding window centered on the real count (ported bugfix, not reintroduced — fixed 0..12 range was a real bug earlier), values or interaction-term (`Δ` both) mode. Split into a cheap synchronous pass (raw non-mulligan curves per row -- evaluate() alone was never the bottleneck) and a batched Worker request for the mulligan adjustment. Used to call optimalMulliganCurve synchronously in a per-row loop -- confirmed directly as a real cause of UI jank (~160ms for the default deck, scaling up with complexity) that ran regardless of which tab was visible, since this component stays mounted in the background. Falls back to raw values for the whole grid (with a visible note) if the search space is too large, rather than a confusing row-by-row mix |
| `src/math/suggestSearch.ts` | single shared dispatch between the fast staircase (frontier.ts) and general brute-force search (generalSuggest.ts) -- convenience one-shot wrapper (`suggestVectors`), no caching. `useSuggestions.tsx` now calls the lower-level pieces directly for the caching benefit; kept here for one-shot use (e.g. tests) |
| `src/math/generalSuggest.ts` | split into `enumerateCompositionCurves` (expensive: every composition's full curve, independent of n/target) and `pickMinimalVectors` (cheap: array scan for a specific goal) -- `generalMinimalVectors` is a thin wrapper doing both for callers that don't need caching |
| `src/state/useSuggestions.tsx` | `SuggestionsProvider`/`useSuggestionsCtx()` -- computes the suggestion search ONCE per goal change and shares it (measured ~5x reduction after deduping 3 independent call sites). ALSO caches the general path's expensive enumeration across goal changes on the same deck+query via a nested memo (confirmed directly: 1 enumeration for a query/deck change, 0 additional enumerations for any number of subsequent goal changes) |
| `src/state/useQueryModel.tsx` | nested memos: the expensive base (parse/normalize/evaluate/decompileFlat) only re-runs on query/groups/deckSize; target changes only re-run the cheap analyze() step on top of it (confirmed via reference-equality test: `result` stays the same object across a target change, `analysis` correctly gets a new one) |
| `src/state/suggestionCurves.ts` | full curves for every distinct minimal suggested composition (via suggestSearch.ts, any query shape), deduped by EXACT curve equality (not visual similarity — confirmed symmetric-vector collapse works, e.g. (9,10)/(10,9) really are one curve) |
| `src/ui/ResultView.tsx` | status line, Chart/Table/Grid/Suggestions tabs (each with a distinct `tab-panel-*` wrapper class). Kept mounted (display-toggled) so switching tabs doesn't reset a tab's own local state. Tab state lives in `App.tsx`'s `Layout`, lifted up so `AdvisorStrip`'s "See suggestions" link can switch it |

Mulligans no longer touch this at all -- the old flat-subtraction approximation (openingHand - mulligans) was measurably wrong (never affected the main curve, only shifted a marker) and has been removed; see mulligan.ts |
| `src/math/mulligan.ts` | EXACT optimal mulligan strategy: enumerate every possible hand composition, recursively compare keep vs. mulligan-and-retry (a fresh full-size hand from the smaller remaining deck), weighted by each hand's own multivariate-hypergeometric probability. No simulation anywhere. Deliberately NOT real London rules (kept hand always full-size, not shrinking) -- an explicit, agreed simplification. Only models the OPENING HAND point exactly; turns 1+ still draw from a single continuous shuffle as before. A real, confirmed consequence: bestP comes out HIGHER than the naive independent-attempts formula 1-(1-p)^(mulligans+1), because a failing hand enriches what's left in the deck -- verified numerically, not assumed. `optimalMulliganCurve` generalizes this to a WHOLE curve (every draw count at once, not just one goal turn) -- evaluate() computes the whole curve internally regardless, the scalar version was simply discarding everything except one index; cross-validated exactly against the scalar function at multiple points. MEMOIZED by `(remaining group counts, mulligans left)`: the recursive value at any point depends only on that state, not the specific sequence of hands that reached it, and different hand sequences routinely land on the same cumulative state (removal is addition, addition is commutative). Measured directly: 2 groups/1 mulligan went from ~500ms to ~99ms, 2 groups/2 mulligans from several seconds to ~164ms, and 3-group cases that were previously rejected outright (too large under the pre-memoization cap) now complete in 1-3s. The size cap (`checkSizeCap`) was recalibrated to reflect the actual memoized cost (sum of per-level state counts) instead of the pre-memoization total PATH count (a product, which had been a severe overestimate) -- and raised further since the computation now runs through a Worker anyway, so a multi-second case no longer needs to be avoided at all costs, just shown with a loading state |
| `src/workers/mulliganProtocol.ts` | message shapes crossing the postMessage boundary. `Float64Array` structured-clones natively (confirmed directly) -- curves don't need conversion to plain arrays. Two request kinds: `single` (advisor strip/Suggestions/chart's one goal-turn point) and `batch` (GridTab's per-swept-row curves, one round trip for every row instead of one per row). Batch carries a `{dnf, sizes}` PAIR per row, not one shared dnf -- normalize()'s subsumption logic can produce a genuinely different Dnf structure per composition (confirmed elsewhere this project), a real bug caught before shipping the first draft of this |
| `src/workers/mulliganWorker.ts` | runs the mulligan computation off the main thread, dispatching on the request's `kind`. Deliberately thin -- imports the SAME already-tested pure functions from mulligan.ts, no new math lives here |
| `src/state/useWorkerRequest.ts` | generic, reusable async-request hook (any Worker-like target, not just this one): staleness handling (a superseded request's late response is discarded, matched by id), loading state, keeps PREVIOUS data visible while a new request is in flight rather than blanking to null. Compares requests by VALUE (JSON fingerprint), not object reference -- an earlier reference-based version OOM-crashed the test runner via an infinite effect loop the moment a caller passed a non-memoized request object (confirmed directly, not a hypothetical) |
| `src/state/mulliganWorkerClient.ts` | lazily creates a real `Worker` (guarded -- jsdom has none at all) or falls back to a synchronous same-interface implementation. The fallback must be a cached singleton, not a fresh instance per call -- a fresh one would give `useWorkerRequest` a different reference every render, needlessly refiring its effect (a real bug, caught before shipping) |
| `src/state/useMulliganStrategy.tsx` | `MulliganStrategyProvider`/`useMulliganStrategyCtx()` -- now runs the mulligan computation through the worker infrastructure above instead of blocking the main thread directly (measured before this change: ~0.5s for 1 mulligan, several seconds for 2 -- confirmed via real Playwright + a real headless Chromium that the page no longer freezes during this, see CLAUDE.md §13). `buildDisplayCurve` remaps the mulligan curve (indexed by extraDraws) onto the same "n = total cards seen" axis the chart/table/grid already use, so the mulligan-adjusted values slot into existing rendering code unchanged. At mulligans=0, exact passthrough of the raw curve (verified, not just "close") |
| `src/math/frontier.ts` | monotone-only: minimal sufficient vectors (greedy descent from the max corner) |
| `src/math/allocate.ts` | slot-budget optimizer: maximize P for a budget (primal), fewest slots for a target (dual) |
| `src/math/expr.ts` (`pruneGroups`) | explicit, user-triggered removal of atoms mentioning a deleted group |
| `src/math/builder.ts` | builder model: query = OR of combos, each combo a plain AND (no per-combo threshold — see PLAN §4c). No "not" toggle -- for integer counts, NOT is fully redundant for >= and <= (rewritten to the direct equivalent comparator: "not >=2" IS "<=1"). NOT of an exact count or a genuine range is a disjoint union, NOT reducible to one row -- correctly refused (falls back to text) rather than silently misrepresented; nothing is lost from the query language, only from what the row builder can directly construct |
| `src/harness/main.ts` | plain-DOM dev harness — deck editor, combo query builder + text, export/import, "path to target" advisor (by-turn draws-vs-copies comparison), Result card (chart/table toggle, steepest-gain marker, starting-hand line, multi-group phantoms + hover/click-to-focus + tooltip), grid (values/Δboth interaction term; Δcopy/Δdraw kept in code, commented out of the UI), frontier |
